# HomeScout Kenya — Architecture

**Status:** Phases 1–16 implemented/prepared. The Android shell, housing marketplace, identity and safety workflows, collaboration, moving/home services, sandbox-ready Daraja payment architecture, consent-based Assistant, staff operations console, and deployment/release preparation are documented. No production deployment occurred.

## Android

The Kotlin app uses Jetpack Compose and Material 3 in one `app` module. The source is separated into `ui/theme`, `ui/components`, `navigation`, `data/remote`, `data/auth`, and feature packages. The bottom bar shows no more than five destinations and adapts to the authenticated account's server-selected active role. Tenant accounts retain Home, Discover, Areas, Finance, and Profile; landlord, agent, property-manager, service-provider, roommate, and staff accounts get role-specific workspaces and tabs. Map, listing management, property detail, private listing preview, collaboration, Services, Trust, and Operations remain secondary destinations unless a role's tab promotes one. Home sample cards remain demo content. The current Map screen uses MapLibre Native and OpenFreeMap public styles, a HomeScout API geocoding proxy, Fused Location Provider on an explicit permission action, and public property records that are published, available, non-demo, and have coordinate provenance.

The Profile feature supports registration, email verification/resend, sign-in, password reset, current-account display, session review/revocation, and permission-gated administration. Phase 7 adds the secondary personal hub for profile/preferences, role switching, saves and collections, activity, schedule, notifications, manual records, documents, support, About, and account settings. The active role is fetched from `/hub/profile` and changed through the server-validated `/hub/profile/active-role` endpoint; Android offers only roles returned as assigned to the current account. Role-specific home cards, drawer actions, and bottom tabs are presentation/navigation scopes. Backend resource permissions remain authoritative and continue to reject unauthorized actions. `PersonalHubApi` uses the same configured versioned API root and bearer session. `AuthController` runs identity operations on a single background executor and publishes immutable Compose state. `EncryptedSessionStore` encrypts the token pair with AES-GCM and an Android Keystore key. Sign-out clears local storage and attempts server-side refresh-session revocation.

Debug builds permit cleartext only for local API development. Release builds use Android's secure cleartext defaults. The API address is not a secret; server credentials never belong in Android source or build configuration.

The release build reads signing inputs from `HOMESCOUT_RELEASE_*` environment variables and checks that the keystore path is absolute and outside the source checkout. `preflightRelease` blocks `assembleRelease`, `packageRelease`, and `bundleRelease` if signing or an HTTPS API URL is missing. Version code/name can be set through Gradle properties or `HOMESCOUT_VERSION_CODE` / `HOMESCOUT_VERSION_NAME`. No signing credentials are configured in this workspace; no signed app bundle was produced. See `RELEASE_CHECKLIST.md`.

No map key is embedded in Android. OpenFreeMap's public tiles are requested directly by MapLibre and require attribution; they are free to use without registration or billing but have no SLA. Kenya area search calls the versioned HomeScout API, which proxies explicit user searches to the configurable Nominatim endpoint and applies an in-memory cache and single-process rate limiter. Production deployments with multiple workers must share rate limiting/caching or use a supported geocoder/self-hosted service. Device location is requested only after user action. Markers require public API listings with paired coordinates and recorded coordinate provenance; demo rows are never queried by the map client. Satellite/terrain imagery, Places results, and nearby amenities are not provided by this setup. See `MAPS_SETUP.md`.

Keep feature rules outside composables. Move map and account controllers to lifecycle-aware ViewModels/repositories if state and feature complexity grow. Pure Kotlin map state/query/parser tests are in `app/src/test/`; add UI/instrumentation tests when the project adds a UI test harness.

Discover and property detail use `MarketplaceApi` and the central `ApiConfiguration`. The Android client sends only the account access token for protected marketplace operations. It has no server-side credentials. Search is debounced and runs off the main thread; adaptive Compose grids respond to available width. When no API base address is configured, discovery shows separately labelled local sample cards instead of claiming those items came from the backend.

## Backend

`backend/` is one FastAPI service organized into API routers, request/response schemas, services, models, database/session, configuration, errors, and logging. `app/main.py` is the application factory. `GET /api/v1/health` is liveness, and `GET /api/v1/health/ready` checks SQL connectivity. Stable error envelopes omit raw inputs and exception details. The app does not create schema at startup. Phase 16 adds a non-root Python 3.12 container with a pinned runtime lock; Docker was unavailable here, so the image has not been built. Container startup does not migrate the schema; run Alembic as a single reviewed release job.

Configuration uses `HOMESCOUT_` environment variables and ignored `backend/.env`. Production requires PostgreSQL, a stable authentication signing key, and SMTP with STARTTLS. Staging also requires the signing key and secure mail. Development may use an ephemeral signing key if none is configured. Development token response exposure is false by default and restricted to development/test.

## Authentication and authorization

- Email/password accounts use Argon2id hashes. Registration creates pending accounts and gives only the tenant role; an elevated role is stored as a request until an operator grants it.
- Email verification and password reset use single-use random codes; the database stores their SHA-256 verifiers. Unknown-address reset requests receive a generic response.
- Access tokens are HS256 JWTs with required issuer, audience, subject, session, token-purpose, and time claims. Refresh tokens are random, hashed in the database, and rotated after use.
- Every protected request checks the JWT and its active, unexpired, unrevoked database session plus the user's active and verified account state. Password reset revokes active sessions.
- Nine persistent roles are seeded by Alembic: tenant, roommate, landlord, real estate agent, property manager, service provider, moderator, admin, and super admin. Guest is a virtual unauthenticated role.
- Permission checks deny by default and combine role permission, owner predicates, and scoped role assignments. Self-registration cannot grant elevated privileges. The admin API requires reauthentication, prohibits self role changes, restricts role-to-scope combinations, and records audited assignments/revocations.
- The first Super Admin is created through `python -m app.cli create-super-admin --email ...`; the CLI prompts for the password and accepts it neither as an argument nor as logged output.

The RBAC catalog defines capability boundaries. Future resource services must also verify that the requester is the actual conversation participant, group member, booking participant, and so on; a permission string alone is not a substitute for resource membership checks.

## M-Pesa payment architecture

Phase 12 adds `/api/v1/payments` and two portable tables: `payment_transactions` and `payment_callback_events`. Daraja OAuth, STK Push, and STK Query are implemented only in the backend with fixed Safaricom sandbox/production hosts. `HOMESCOUT_MPESA_*` settings are disabled by default; production additionally requires a production environment and explicit service-collection authorization. Consumer key, consumer secret, passkey, shortcode, callback host, and HMAC key are never returned by APIs. The app's only supported purpose is `service_booking`; rent collection, escrow, provider payout, and refunds are excluded.

Only a customer-owned, provider-accepted service order with fixed pricing and a positive integer KES amount is eligible. A database idempotency key and partial unique indexes prevent duplicate active or successful attempts for the same order. The system stores a phone HMAC and last four digits, not the full phone. Each callback is bounded/validated, matched to its stored checkout and merchant identifiers, reduced to minimal hashed evidence, then checked using Daraja STK Query before state can become terminal. Unknown or mismatched callbacks do not mutate transactions. Callback and user/admin reconciliation share a cooldown; an ambiguous STK network submission stays pending and is never automatically resent. A server-side verified status is the only source for success; a receipt is exposed only when callback metadata matches the original amount and phone and contains a valid receipt identifier.

The callback endpoint has no secret in its URL because proxy access logs often record paths. It cannot authenticate the caller by a signature, so it treats callback data as untrusted and queries Safaricom over the authenticated API. Internal processing failures return a temporary error response; unknown or malformed callbacks receive a generic acknowledgment. `reversed` is a persisted status reserved for an authenticated provider status response that explicitly reports reversal; no reversal/refund operation is initiated in this phase. The Daraja portal is the source for app credentials, environment setup, and API contract; detailed STK field requirements must still be confirmed in the owner's selected Daraja app before enabling real traffic.

## Location and property foundations

Phase 4 adds `countries`, `counties`, `towns`, `neighbourhoods`, `properties`, and `property_media`. County/town/neighbourhood foreign keys and validation preserve the hierarchy. County and location rows retain source names/URLs and optional metadata. Coordinates are optional; latitude and longitude must be paired and have a recorded source. Seeded reference rows carry no coordinates because none were sourced.

Property rent is stored as fixed-precision decimal KES with an explicit rent frequency. `property_type` records the building type; `unit_type` records bedsitter/studio/bedroom configuration; `accommodation_type` records whole, shared, or student accommodation. Property media separates images, videos, and floor plans and can mark stock imagery as illustrative. Owner is required; agent and manager references are optional and are not assignable through Phase 4 APIs.

Location reads/search are public, while adding towns or neighbourhoods requires `location:manage:global`. Public property search returns only published, available, non-demo records and supports county/town/neighbourhood ID, title/description/location query, KES rent, bedrooms, building/unit type, furnishing, normalized amenity, verified-only, and map viewport filters, plus deterministic sorting. Property creation starts a draft. A landlord can edit their own listing; an agent can create and manage a listing only under an active owner mandate. Owners can also grant an eligible agent or property manager an assignment for one listing. Public details hide private drafts; the owner and authorized parties use a separate preview route.

The marketplace migration adds normalized property amenities and separate records for saved listings, search history, saved-search alerts, listing mandates, enquiries, and listing reports. Search history and alert counts are capped. Saved-search records have no delivery worker. Enquiries are visible to their sender and authorized recipient; no owner contact details are returned by the public property API. Phase 9 adds a permission-gated human review queue for reports; allegations alone do not alter a user's standing or hide a listing.

Phase 10 adds participant-scoped conversations for existing property enquiries, accepted roommate connections, and active shared-group membership. Message bodies are AES-GCM encrypted at rest with `HOMESCOUT_MESSAGE_ENCRYPTION_KEY`; authorization, block status, per-user rate limits, and membership are checked server-side. Message reports are stored for follow-up; this phase does not include a moderation queue for those reports. Attachment references are restricted to participant-visible private documents, but the Phase 7 development files themselves are not encrypted by this message cipher.

## Personal hub and private account data

Phase 7 adds account preferences, saved hub items, saved collections and explicit sharing records, personal activity, schedule entries, manual KES records, private documents, support tickets/messages, and deletion requests. Profile and notification records gain fields used by those screens. All APIs require an authenticated account; personal rows are owner-scoped. Shared collections disclose their owner edit capability to the recipient but do not disclose the owner's other share recipients. Role switching is restricted to roles already assigned by an authorized process. `Africa/Nairobi` is the schedule default; clients can submit another valid timezone.

The personal hub sits behind the Profile tab as secondary routes, keeping the primary navigation at five tabs. Saved searches reopen their stored filters in Discover. Activity captures supported marketplace and account events; it is not a complete event stream for future services. Notification records and preferences are in-app only. Schedule reminder values are stored without a scheduler or delivery worker. KES records are user-entered notes, not processor-confirmed payments. Account deletion is a password-reauthenticated request that remains pending for an operational processor. Phase 14 adds the staff operations console as another secondary route from Profile; it uses server permissions for all actions and does not add a sixth bottom tab.

Private profile photos and personal documents use configurable development local disk storage. Document uploads have a configurable 15 MiB default cap and validate allowed document signatures; reads and deletes are authenticated and owner-checked. Phase 9 verification evidence is encrypted at rest with AES-GCM using `HOMESCOUT_TRUST_ENCRYPTION_KEY`; original downloads are decrypted only for the owner or an authorized reviewer, with reviewer access audited. Other personal documents remain local files without this feature-specific encryption. Production object storage, managed key custody, malware scanning, retention, and backup are not configured. Phase 14 adds an authorized staff queue for support tickets, assignment, priority, escalation, replies, and action history; ticket bodies are withheld from queue summaries and detail access is audited.

## Staff operations and moderation

## SmartRent housing finance and learning

Phase 8 adds authenticated `/api/v1/finance` endpoints and a secondary experience inside the existing Finance tab. It stores owner-scoped profiles, move-in plans, savings goals and contributions, financial records, lesson progress, cost comparisons, lease/deposit notes, and in-app alerts. Explicit savings-goal shares are limited to named accounts and contribution permission; they expose only the shared virtual goal, not a user's profile or other finance data.

Sensitive planning fields and personal finance-note payloads are JSON-serialized then encrypted with AES-GCM. Each ciphertext includes a fresh 96-bit nonce, and the account UUID is authenticated associated data, so another account cannot decrypt a copied payload. The 256-bit base64 key comes from `HOMESCOUT_FINANCE_ENCRYPTION_KEY`; it is required in staging/production and never returned by APIs. Key loss makes these encrypted payloads unreadable. Key rotation needs a planned data re-encryption procedure. Relational identifiers, ownership, dates, statuses, and other operational metadata remain in normal database columns; encryption does not cover uploaded private document bytes. Those continue to use Phase 7 development local disk storage.

RentScore and related estimates are deterministic planning aids based on user-entered KES values, not credit, eligibility, or lending decisions. Variable/seasonal income uses recent user-entered months where available; otherwise documented default factors are shown. Savings goals are virtual trackers and do not receive, hold, or transfer funds. Rent entries are manual notes and do not confirm a transaction. Utility summaries are derived only from user-provided values; the Lease Guardian organizes dates and questions and is not legal advice. Budget discovery filters currently published listings; no inventory is bundled with the feature. Alerts are in-app records only. Financial literacy includes quizzes and links to official safety sources. The Assistant is a separate Phase 13 feature and remains disabled until configured.

SmartRent Phase 5 adds owner-scoped rent obligations and payment reports. Obligation and report payloads use the existing AES-GCM Finance cipher. A report represents a payment the user says was made elsewhere; the API labels it unverified, tracks partial totals, and prevents retries from duplicating reports. It does not contact a landlord/provider and cannot prove receipt. The Android Payments route lists rent reminders/reports independently from Daraja transaction history. M-Pesa remains limited to eligible service bookings; card and PayPal rent checkout are unavailable. Do not add rent custody or infer that user-reported amounts are settled.

## Trust, verification, and rental safety

Phase 9 adds `/api/v1/trust` workflows for landlord, agent, service-provider, and property verification. Submissions require evidence references and enter `pending`; an authorized administrator manually approves or rejects them. Reviews record actor, time, status change, submission number, and an encrypted private note. Rejected requests can be resubmitted with new evidence; approvals can expire. These are HomeScout review states, not third-party identity, title, tenancy, or license checks. The owner-specific verification API shows the owner their own history; only authorized reviewers see the review queue and can fetch evidence. Evidence downloads are audited.

Listing and safety reports encrypt narrative details, keep the owner's report list private, and attach evidence through owner-owned private-document records. A reviewer can set `in_review`, escalate, resolve, or dismiss and can explicitly hide, restore, or remove a property when resolving a listing report. Listing visibility changes only on that explicit moderator action. Exact normalized-address duplicates and sufficiently comparable rent outliers are review prompts only; they create neither a fraud determination nor an automatic restriction. Public property trust indicators expose only current recorded verification/account-contact status and explain their limits. They do not claim ownership, authorization, reviews, a trust score, or availability.

Safe-viewing plans store meeting point, trusted-contact details, notes, times, and check-in/out privately. Details are shared only to a named HomeScout account after explicit owner consent; reads remain owner/recipient-scoped. Incident reports have their own owner-private queue and human review history. The guide/checklist is informational. No external contact messages, reminder delivery, emergency response service, phone-pattern analytics, or automatic criminal/fraud labeling is included. The Android Trust & safety screen is a secondary Profile route; property details link to safe viewing and display only returned indicators. The HomeScout primary navigation remains five tabs.

Phase 10 adds host-confirmed viewing requests, rescheduling, cancellation, completion history, agenda synchronization, and in-app notifications. A request remains `requested` until the assigned host confirms; a request itself never confirms a time. Private comparison boards and journal contents use the Phase 10 AES-GCM cipher. Group shared searches, shared properties, votes, comments, tasks, comparisons, and moving goals require active group membership. Journal sharing is explicit and can be revoked. Roommate discovery is opt-in; candidate responses omit contact details, and conversation creation requires an accepted connection. Group financial goal amounts are not returned to members until each member explicitly consents.

The Phase 10 Android collaboration screen is a secondary route from Profile and property detail. It does not add bottom tabs. Notifications/reminders are persisted in-app records only; there is no push/email delivery worker. Viewing journal photo references use the existing private-document store, and voice-note recording/upload is not implemented.

Phase 11 adds `/api/v1/services` for provider discovery/profile/offering administration, county service areas, provider photos, booking lifecycle and reviews, KES service order records, resident access grants, maintenance tickets/photos/history, and private moving plans/tasks/calendar/budgets/room setup. The Android Services workspace is a secondary route, retaining the five primary tabs. Provider approval is derived from the current HomeScout manual verification record; no external identity, license, or insurance provider is connected. Bookings start pending and need provider/customer actions; a recorded order is not a payment. Moving plans and room setup are owner-private. Residents can open maintenance requests only for properties explicitly granted by a current owner/manager access record; providers see only requests assigned to them. Revoking resident access blocks subsequent reads, including older related requests. Provider and maintenance media use development local storage, and no external notification/calendar worker is connected.

Listing media uploads are streamed through a size-limited endpoint and restricted to JPEG, PNG, or WebP signatures. The current `LocalMediaStorage` writes UUID-keyed objects outside public web roots, checks path containment, and serves authenticated draft images or public listing images with `nosniff`. Its filesystem path is environment-configured. Production object storage, scanning, transformation, backups, and CDN configuration are not implemented. Publishing requires available status plus an uploaded non-illustrative image; it does not mark a listing as verified. Synthetic fixtures remain constrained to draft, unverified, and availability-unknown states.
